* Overview

Claude Code IDE for Emacs provides native integration with Claude Code CLI through the Model Context Protocol (MCP). Unlike simple terminal wrappers, this package creates a bidirectional bridge between Claude and Emacs, enabling Claude to understand and leverage Emacs' powerful features—from LSP and project management to custom Elisp functions. This transforms Claude into a true Emacs-aware AI assistant that works within your existing workflow and can interact with your entire Emacs ecosystem.

** Features

- Automatic project detection and session management
- Terminal integration with full color support using =vterm=, =eat=, or =ghostel=
- MCP protocol implementation for IDE integration
- Tool support for file operations, editor state, and workspace info
- Extensible MCP tools server for accessing Emacs commands (xrefs, tree-sitter, project info, e.g.)
- Diagnostic integration with Flycheck and Flymake
- Advanced diff view with ediff integration (modify suggestions before applying)
- Tab-bar support for proper context switching
- Selection and buffer tracking for better context awareness

** Emacs Tool Integration

This package enables Claude Code to leverage the full power of Emacs through MCP tools integration. Claude can directly access and utilize Emacs capabilities including:

- *Language Server Protocol (LSP)* integration through xref commands for intelligent code navigation (eglot, lsp-mode and others)
- *Tree-sitter* for syntax tree analysis and understanding code structure at the AST level
- *Imenu* for structured symbol listing and navigation within files
- *Project* integration for project-aware operations
- *Any Emacs command or function* can be exposed as an MCP tool, allowing Claude to:
  - Perform project-wide searches and refactoring
  - Access specialized modes and their features
  - Execute custom Elisp functions tailored to your workflow

This deep integration means Claude Code understands your project context and can leverage Emacs' extensive ecosystem to provide more intelligent and context-aware assistance.

* Installation

** Prerequisites

- Emacs 28.1 or higher
- Claude Code CLI installed and available in PATH
- =vterm=, =eat=, or =ghostel= package (for terminal support)

** Installing Claude Code CLI

Follow the installation instructions at [[https://docs.anthropic.com/en/docs/claude-code][Claude Code Documentation]].

** Installing the Emacs Package

Currently, this package is in early development.

To install using =emacs-version= >= 30 and =use-package= with the =vc= binding:

#+begin_src elisp
(use-package claude-code-ide
  :vc (:url "https://github.com/manzaltu/claude-code-ide.el" :rev :newest)
  :bind ("C-c C-'" . claude-code-ide-menu) ; Set your favorite keybinding
  :config
  (claude-code-ide-emacs-tools-setup)) ; Optionally enable Emacs MCP tools
#+end_src

To install using =use-package= and [[https://github.com/raxod502/straight.el][straight.el]]:

#+begin_src emacs-lisp
(use-package claude-code-ide
  :straight (:type git :host github :repo "manzaltu/claude-code-ide.el")
  :bind ("C-c C-'" . claude-code-ide-menu) ; Set your favorite keybinding
  :config
  (claude-code-ide-emacs-tools-setup)) ; Optionally enable Emacs MCP tools
#+end_src

*** Doom Emacs

In =packages.el=:

#+begin_src emacs-lisp
(package! claude-code-ide
  :recipe (:host github :repo "manzaltu/claude-code-ide.el"))
#+end_src

In =config.el=:

(use-package! claude-code-ide

After saving the above, run: =doom sync= in the terminal.

*** From a local checkout

Use a local checkout to run a branch that is not on the package archives, for example a fork's =session-registry= branch with the session registry and the status buffer.

1. Get the code. Any folder works; the examples use =~/Source/claude-code-ide.el=:

   #+begin_src bash
   git clone https://github.com/<you>/claude-code-ide.el ~/Source/claude-code-ide.el
   cd ~/Source/claude-code-ide.el
   git checkout session-registry
   #+end_src

   Or keep your usual branch checked out and put the branch in a worktree: =git worktree add .worktrees/session-registry session-registry=.

2. Load the package from that folder, and nowhere else. Do not use =:vc= or =:straight= for it: such an install puts its own copy early in =load-path=, and that copy hides the checkout without any warning. Use =:demand t=, so that the modes below are on before the first session starts:

   #+begin_src elisp
   (defconst my/claude-code-ide-dir
     (expand-file-name "~/Source/claude-code-ide.el")  ; or the worktree folder
     "The claude-code-ide.el checkout that this Emacs loads.")

   (use-package claude-code-ide
     :load-path my/claude-code-ide-dir
     :demand t
     :bind ("C-c C-'" . claude-code-ide-menu)
     :config
     ;; Optional: Claude Code uses your claude.ai login, not an API key
     ;; that the Emacs environment holds for other packages.
     (setq claude-code-ide-cli-environment-unset '("ANTHROPIC_API_KEY"))
     ;; Record sessions for restore, and show their live status.  The
     ;; checks keep this file working with a checkout that lacks the modes.
     (when (fboundp 'claude-code-ide-session-registry-mode)
       (claude-code-ide-session-registry-mode 1))
     (when (fboundp 'claude-code-ide-session-status-mode)
       (claude-code-ide-session-status-mode 1)))
   #+end_src

3. Remove an installed copy, if one exists. Look for =~/.emacs.d/elpa/claude-code-ide*=. Delete it with =M-x package-delete=, or move the folder out of =elpa=. Also remove =claude-code-ide= from =package-vc-selected-packages= in your custom settings, or Emacs installs it again.

4. Restart Emacs, and check:

   #+begin_src elisp
   (locate-library "claude-code-ide")       ; must name your checkout
   claude-code-ide-session-registry-mode    ; must be t
   #+end_src

Sessions that already run when the registry turns on are recorded too, but without status hooks; =M-x claude-code-ide-session-registry-track-sessions= restarts them with hooks (see [[*Session Registry and Restore][Session Registry and Restore]]).

*** Updating in a running Emacs

After an update of the installed package, =M-x claude-code-ide-reload= loads its files again, each after the files that it requires, without a restart. Running sessions keep running. The command reports each file that fails to load, and it turns each package mode that is on off and on again, so that the mode gets the hooks of the new version. A checkout on =load-path= has no generated autoloads: run =M-x load-library RET claude-code-ide-reload RET= one time first. See [[file:docs/updating.md][docs/updating.md]] for the update command of each kind of install, and for what a reload cannot change.

* Usage

** Basic Commands

The easiest way to interact with Claude Code IDE is through the transient menu interface, which provides visual access to all available commands. Simply run =M-x claude-code-ide-menu= to open the interactive menu.

| Command                                 | Description                                       |
|-----------------------------------------+---------------------------------------------------|
| =M-x claude-code-ide-menu=                | Open transient menu with all Claude Code commands |
| =M-x claude-code-ide-emacs-tools-setup=   | Set up built-in MCP tools (e.g. xref, project)    |
| =M-x claude-code-ide=                     | Start a new instance of the current provider      |
| =M-x claude-code-ide-toggle-provider=     | Make the next provider the current provider       |
| =M-x claude-code-ide-codex=               | Start a new Codex instance for the project        |
| =M-x claude-code-ide-send-prompt=         | Send prompt to Claude from minibuffer input       |
| =M-x claude-code-ide-continue=            | Continue most recent conversation in new instance |
| =M-x claude-code-ide-resume=              | Resume a previous conversation in new instance    |
| =M-x claude-code-ide-stop=                | Stop a Claude Code instance of the project        |
| =M-x claude-code-ide-stop-all=            | Stop all instances in the project (=C-u=: global)   |
| =M-x claude-code-ide-rename-session=      | Rename a Claude Code instance                     |
| =M-x claude-code-ide-switch-to-buffer=    | Switch to a Claude buffer of the project          |
| =M-x claude-code-ide-list-sessions=       | List all active Claude Code instances and switch  |
| =M-x claude-code-ide-check-status=        | Check if Claude Code CLI is installed and working |
| =M-x claude-code-ide-insert-at-mentioned= | Send selected text to Claude prompt               |
| =M-x claude-code-ide-clear-selection=     | Drop the file/selection shown in Claude's prompt  |
| =M-x claude-code-ide-send-escape=         | Send escape key to Claude terminal                |
| =M-x claude-code-ide-insert-newline=      | Insert newline in Claude prompt (sends \ + Enter) |
| =M-x claude-code-ide-toggle=              | Show/hide the project's Claude windows            |
| =M-x claude-code-ide-toggle-recent=       | Show/hide all Claude windows globally             |
| =M-x claude-code-ide-show-all=            | Show every instance of the project (=C-u=: global)  |
| =M-x claude-code-ide-attach-to-tab=       | Attach the instance of this buffer to this tab    |
| =M-x claude-code-ide-show-debug=          | Show the debug buffer with WebSocket messages     |
| =M-x claude-code-ide-clear-debug=         | Clear the debug buffer                            |

Commands that target one instance (stop, switch, send-prompt, insert-at-mentioned, clear-selection, escape, newline) resolve their target automatically: the Claude terminal you are in, the project's only instance, or its only visible one; beyond that, send-type commands use the most recently used instance (echoing the choice) while =claude-code-ide-stop= asks. A prefix argument (=C-u=) always lets you pick the instance explicitly.

** Multiple Projects and Instances

Claude Code IDE automatically detects your project using Emacs' built-in =project.el=, and any project can run several Claude Code instances at the same time — for example one instance refactoring while another answers questions.

- The first instance of a project gets the plain buffer name =*claude-code[project-name]*=.
- Running =M-x claude-code-ide= again starts an /additional/ instance and prompts for an optional name: entering =refactor= yields =*claude-code[project-name:refactor]*=, while empty input auto-numbers (=*claude-code[project-name:2]*=, =*claude-code[project-name:3]*=, ...). Auto numbers are positional and get reused after an instance exits.
- =M-x claude-code-ide-rename-session= renames an instance later; names show up in buffer names, session lists and prompts.
- Each Claude Code instance runs its own IDE server, so cursor/selection context is shared with /every/ Claude Code instance of the project, while explicit actions (prompts, at-mentions, diffs) target exactly one.
- Use =claude-code-ide-list-sessions= to see all instances across all projects and switch between them.

Note for =claude-code-ide-continue=: starting a second continued instance in the same directory forks the same "most recent" conversation — that is CLI behavior.

** Providers: Claude Code and Codex

A provider is a coding-agent CLI. The package has two: =claude= (Claude Code) and =codex= (Codex). Codex and Claude Code instances can run in one project at the same time.

*** The current provider

- =M-x claude-code-ide=, =claude-code-ide-continue= and =claude-code-ide-resume=, and their keys =s=, =c= and =r= in =claude-code-ide-menu=, start an instance of the /current provider/.
- The menu shows the current provider in its header. Its key =P= toggles the current provider between the registered providers, and the menu stays open.
- =C-u= before one of the three commands asks for the provider, with completion and the current one as the default. Then it asks for the instance name, as =C-u= always does.
- The current provider is the one that you used last. It persists across Emacs restarts, in the file =current-provider= in the report directory of the session registry (=claude-code-ide-provider-file= changes the file). A missing or broken file gives =claude-code-ide-default-provider= (default =claude=).
- A restore or a reopen of a saved session uses the provider of that session, never the current provider.

*** Codex

- =M-x claude-code-ide-codex= starts a Codex instance in the current project, and makes Codex the current provider. =claude-code-ide-codex-continue= and =claude-code-ide-codex-resume= continue the last conversation or open the picker.
- A Codex instance with the role =coordinator= may call the coordinator tools that only read (=claude-code-ide-codex-coordinator-approved-tools=: list, inspect, request-status and handover-status) without approval. Launch, resume, stop, submit-prompt and handover ask for approval. Another instance gets no approval for any coordinator tool.
- Emacs passes its instructions, the MCP tools server, and the approvals with =-c= options. Prompts go through =codex queue=. See [[file:docs/codex.md][docs/codex.md]].
- A Codex instance gets no IDE server and no lock file in =~/.claude/ide/=, because Codex does not speak that protocol. It uses only the MCP tools server.
- Codex never gets =claude-code-ide-cli-extra-flags= or the Claude Code model. Its flags and its model come from =claude-code-ide-codex-extra-flags=.
- You answer the Codex folder trust dialog yourself, one time for each repository.
- Codex runs the status hooks only after you trust them. You need not remember a command for it: the first Codex start from a command (=M-x=, or the menu) shows the hook commands and asks you one time. After your yes, Emacs writes the trust through Codex, and the instance starts with status. After a no, the instance runs without status, and Emacs does not ask again until you restart Emacs.
- =M-x claude-code-ide-restore-sessions= asks at most one time for the whole restore. The automatic restore at the start of Emacs, a coordinator launch and a timer never ask; they get the hooks only when Emacs knows that they are trusted. See [[file:docs/status-events.md][docs/status-events.md]], section "Hook trust".
- Options: =claude-code-ide-codex-cli-path=, =claude-code-ide-codex-extra-flags=, =claude-code-ide-codex-remove-openai-api-key= (default t), =claude-code-ide-codex-no-alt-screen= (default t), =claude-code-ide-codex-skip-update-check= (default t), =claude-code-ide-codex-config-read-timeout= (5 s), =claude-code-ide-codex-queue-timeout= (30 s), =claude-code-ide-codex-coordinator-approved-tools=.

** Stopping Instances

When Emacs stops an instance, or quits, it sends the CLI its soft end (SIGHUP), waits, and then ends the background commands that the CLI started and that still run. At an Emacs quit, all CLIs share one short wait. When a CLI exits by its own choice (for example "Move to background and exit"), Emacs leaves its background work running.

The options are in the group =claude-code-ide-process=: =claude-code-ide-process-stop-timeout= (5 s), =claude-code-ide-process-quit-timeout= (1.5 s), =claude-code-ide-process-kill-wait= (2 s), =claude-code-ide-process-soft-end=, and =claude-code-ide-process-lsof-timeout= (30 s), which limits the scan of working folders. See [[file:docs/process-tree.md][docs/process-tree.md]].

** Editor Context

Every instance of a project is told which file you are looking at and which text you have selected. The Claude prompt shows this as an =⧉ In file.el= or =⧉ 3 lines selected= label, and the prompt you submit next carries a short reminder ("The user opened the file … in the IDE" or the selected lines). The file's content itself is not sent.

- =M-x claude-code-ide-clear-selection= (=x= in the menu, =C-c C-x= in the Claude terminal) drops that context from one instance, like the =x= next to the file name in the VS Code extension. The dismissed file stays out of the prompt while you move around in it; selecting a region or visiting another file shares context again.
- Set ~claude-code-ide-share-opened-file~ to =nil= (or toggle it under =o= in the configuration menu) to report only selected regions. The file you are in is then never mentioned; a region is shared while it is active and dropped when it is deactivated.

** Window Management

- Each instance owns its own side-window slot, so several instances can be visible side by side along =claude-code-ide-window-side=; instances of the same project are grouped next to each other. Emacs' =window-sides-slots= controls how many side windows fit per side; heavy users can e.g. =(setq window-sides-slots '(nil nil 3 nil))= for three windows on the right side
- =claude-code-ide-toggle= works as a project panel: it hides all of the project's visible Claude windows (remembering the set) or restores them; with =C-u= it toggles a single chosen instance
- With =tab-bar-mode=, tabs keep independent window layouts, and the toggles follow that model: hiding and restoring apply to the current tab only, and each tab remembers its own sets. Newly created tabs never inherit Claude windows from the cloned layout — use =claude-code-ide-show-all= or the toggles to summon instances into a fresh tab
- An instance's diffs open in the tab it is attached to: the tab it was started in, or last shown in with =claude-code-ide-toggle=. =claude-code-ide-attach-to-tab=, run in a Claude buffer, attaches that instance to the current tab
- The window can be closed with standard Emacs window commands (=C-x 0=) without stopping Claude
- Use =claude-code-ide-toggle-recent= to hide/show all Claude windows from anywhere, regardless of your current project context. This is useful when you're outside a project directory but want to quickly hide/show Claude

** Diff Viewing with Ediff

When =claude-code-ide-use-ide-diff= is enabled (default), Claude's code suggestions are displayed using Emacs' powerful =ediff= interface. This provides two key advantages:

1. *Visual diff comparison* - See exactly what Claude wants to change with side-by-side or unified diff views
2. *Interactive editing* - You can modify Claude's suggestions before applying them

*** How to use ediff:

1. When Claude suggests code changes, =ediff= opens automatically
2. The ediff control buffer becomes active (a small window with ediff commands)
3. Buffer A shows the current code, Buffer B shows Claude's suggestion
4. You can modify Buffer B to refine Claude's proposed changes
5. Press =q= in the ediff control buffer to quit
6. When prompted, choose whether to accept the changes (=y= or =n=)
7. If you accept (=y=), any changes from Buffer B will be sent back to Claude to be applied on the original file

This allows you to refine Claude's suggestions before they're applied, ensuring the final code meets your exact requirements.

*** Dedicated diff frames stay with their review

- A new terminal window (a launch, resume, restore, or handover target) never goes into a dedicated diff frame. It goes to another frame, and the diff frame keeps the focus.
- A frame with an open ediff, also a suspended one, is never deleted by the end of another instance.
- =claude-code-ide-ediff-files-in-frame= queues a diff while its frame has an open ediff. The diff opens when the ediff before it ends.
- =openDiff= never takes a frame with an open ediff: it uses the frame "ediff LABEL <2>" and so on.
- See [[file:docs/review.md][docs/review.md]].

*** Side Window Configuration

Claude Code buffers open in a side window by default. You can customize the placement:

#+begin_src emacs-lisp
;; Open Claude on the left side
(setq claude-code-ide-window-side 'left)

;; Open Claude at the bottom with custom height
(setq claude-code-ide-window-side 'bottom
      claude-code-ide-window-height 30)

;; Open Claude on the right with custom width
(setq claude-code-ide-window-side 'right
      claude-code-ide-window-width 100)

;; Don't automatically focus the Claude window
(setq claude-code-ide-focus-on-open nil)

;; Keep focus on ediff control window when opening diffs
(setq claude-code-ide-focus-claude-after-ediff nil)

;; Hide Claude window during ediff for more screen space
(setq claude-code-ide-show-claude-window-in-ediff nil)

;; Disable IDE diff viewer to show diffs in terminal instead
(setq claude-code-ide-use-ide-diff nil)
#+end_src

The side window keeps its width (left/right) or height (top/bottom) when the frame is resized or windows are balanced, so the terminal does not reflow its output. Dragging the window's divider still resizes it; displaying the buffer again restores the configured size.

Or, if you'd prefer to use a regular window:

#+begin_src emacs-lisp
;; Use regular window instead of side window
(setq claude-code-ide-use-side-window nil)
#+end_src

*** Terminal Backend Configuration

Claude Code IDE supports =vterm=, =eat=, and =ghostel= as terminal backends, with =vterm= used by default.

*Note:* Of the available backends, =ghostel= delivers the smoothest experience: its rendering is largely free of the flickering, scrolling glitches, and display artifacts that =vterm= and =eat= are prone to, so if it is available in your setup it is the recommended choice.

To switch to another backend:

#+begin_src emacs-lisp
;; Use eat instead of vterm
(setq claude-code-ide-terminal-backend 'eat)

;; Use ghostel instead of vterm
(setq claude-code-ide-terminal-backend 'ghostel)

;; Or switch back to vterm (default)
(setq claude-code-ide-terminal-backend 'vterm)
#+end_src

The =eat= backend is a pure Elisp terminal emulator that may work better in some environments where =vterm= compilation is problematic. The =ghostel= backend uses Ghostel's terminal integration and requires a version that provides =ghostel-exec=. All backends provide full terminal functionality including color support and special key handling.

**** Inline Renderer (Recommended)

Claude Code can render its interface either inline or in fullscreen mode, the latter drawing on the terminal's alternate screen buffer the way =vim= or =htop= do. Inside Emacs — especially with the recommended =ghostel= backend — the inline renderer is the better choice: the transcript lives in the terminal buffer as ordinary text, so you can scroll through the whole conversation and search it with isearch (=C-s= / =C-r=) like in any other buffer. With fullscreen rendering, only the currently visible screen exists in the buffer, and scrolling and searching have to go through Claude Code's own transcript view.

To make sure Claude Code always uses the inline renderer, set =tui= to =default= in its user settings (=~/.claude/settings.json=):

#+begin_src json
{
  "tui": "default"
}
#+end_src

Running =/tui default= inside a session switches the renderer immediately and saves the same setting.

Relatedly, the =claude-code-ide-no-flicker= option sets =CLAUDE_CODE_NO_FLICKER=1=, which enables the fullscreen renderer as a workaround for flickering in =vterm= and =eat=. With the =ghostel= backend flickering is not an issue, so it is best left at its default =nil=.

**** vterm Rendering Optimization

Claude Code IDE includes intelligent flicker reduction for vterm terminals to provide smoother visual output:

#+begin_src emacs-lisp
;; Enable/disable vterm anti-flicker optimization (enabled by default)
(setq claude-code-ide-vterm-anti-flicker t)

;; Adjust the render delay for batching updates (default is 0.005 seconds)
(setq claude-code-ide-vterm-render-delay 0.01)  ; Increase for smoother but less responsive
#+end_src

This optimization detects rapid terminal redraw sequences (like when Claude expands text areas) and batches them for smoother rendering. The 5ms default delay provides optimal visual quality with imperceptible latency.

**** Terminal Initialization Delay

Claude Code IDE includes a brief initialization delay when launching terminals to ensure proper layout rendering:

#+begin_src emacs-lisp
;; Adjust the terminal initialization delay (default is 0.1 seconds)
(setq claude-code-ide-terminal-initialization-delay 0.15)

;; Or disable it entirely (may cause visual glitches)
(setq claude-code-ide-terminal-initialization-delay 0)
#+end_src

This delay prevents display artifacts such as misaligned prompts and incorrect cursor positioning that can occur when terminal emulation is initializing. The default 100ms delay is imperceptible but ensures reliable terminal startup.

**** C-g Opening an External Editor (ghostel)

The =ghostel= backend forwards =C-g= to the terminal, where Claude Code binds =Ctrl+G= to its "edit prompt in external editor" action — so =C-g= opens a prompt-editing buffer instead of quitting. To move the action to another key, rebind it in =~/.claude/keybindings.json= (applies to newly started sessions):

#+begin_src json
{
  "$schema": "https://www.schemastore.org/claude-code-keybindings.json",
  "bindings": [
    {
      "context": "Chat",
      "bindings": {
        "ctrl+g": null,
        "alt+e": "chat:externalEditor"
      }
    }
  ]
}
#+end_src

=alt+e= is a good replacement because ghostel forwards it to the terminal, unlike the action's other default binding =Ctrl+X Ctrl+E= (=C-x= is kept by Emacs).

**** Terminal Reflow Glitch Prevention

Claude Code repaints its screen whenever the terminal is resized ([[https://github.com/anthropics/claude-code/issues/1422][#1422]]). After the terminal reflows, that repaint makes =vterm= and =eat= scroll uncontrollably and writes earlier output into the =ghostel= scrollback a second time. To avoid the most frequent trigger, Claude Code IDE resizes a Claude Code terminal only when its window's width changes. A height-only change — showing or hiding another instance on the same side, a change of the frame height, a multi-line echo area message — keeps the terminal's row count, so the terminal can be taller or shorter than its window until the next width change. This applies to all three backends, is enabled by default and takes effect when the first Claude Code instance starts. To disable it:

#+begin_src emacs-lisp
(setq claude-code-ide-prevent-reflow-glitch nil)
#+end_src

*** Connection Security

Each instance's WebSocket server listens on =127.0.0.1= only, but that address is reachable by every program on the machine, including web pages open in a browser. Each instance therefore writes a random token to its lockfile in =~/.claude/ide/= and accepts a connection only if it presents that token, as the Claude Code CLI does. Connections from web browsers, recognized by their =Origin= header, are always refused.

On Linux, macOS and other POSIX systems the lockfile is readable only by you. On Windows its access follows the permissions of the directory it is in.

If you use a Claude Code CLI version that does not send the token, you can turn the check off for instances started afterwards:

#+begin_src emacs-lisp
(setq claude-code-ide-mcp-require-auth-token nil)
#+end_src

*** Custom Buffer Naming

You can customize how Claude Code buffers are named. The function receives the project directory and, optionally, the instance name (nil for the first, unnamed instance of a project):

#+begin_src emacs-lisp
(setq claude-code-ide-buffer-name-function
      (lambda (directory &optional instance-name)
        (let ((project (if directory
                           (file-name-nondirectory (directory-file-name directory))
                         "Global")))

#+end_src

Existing single-argument functions keep working: they are called with just the directory, and for named instances the name is spliced into the result (a =...]*= suffix becomes =...:NAME]*=) or appended as =<NAME>=.

** Session Registry and Restore

The session registry records each Claude Code instance that Emacs starts. After a crash of Emacs or of the machine, one command starts again every instance that was open, with the same conversation, directory, buffer name, model and flags.

To enable it, put this in your init file:

#+begin_src elisp
(claude-code-ide-session-registry-mode 1)
;; Optional; this is the default
(setq claude-code-ide-state-file "~/.emacs-claude-code-ide-state.json")
#+end_src

When the mode turns on, it also records the instances that already run in this Emacs. Their session id comes from the file that each CLI process keeps in =~/.claude/sessions=, and the registry reads it again every minute and at exit, because =/clear= changes it. These instances have no status hooks. The status buffer shows their state from that file (busy, idle, or a background shell), marked "From CLI status"; a session without a matching file shows as =NO SIGNAL=. =M-x claude-code-ide-session-registry-track-sessions= restarts them with hooks (=T= does it for the session on a line of the status buffer): each resumes its conversation with its instance name, title and model, and a note as its first message tells it to re-arm its background tasks, which end. A session that is busy is skipped unless you give a prefix argument.

*** States

| State      | Meaning                                                                             |
|------------+-------------------------------------------------------------------------------------|
| =pending=  | Emacs starts the instance, or it runs and its conversation ID is not known yet (a Codex conversation before its first prompt). |
| =open=     | The instance runs, or it ran when its Emacs crashed. =claude-code-ide-restore-sessions= starts these again. |
| =closed=   | The instance ended, its buffer was killed, or Emacs exited normally. =claude-code-ide-reopen-session= starts it again. |
| =failed=   | The last restore or reopen failed; the list shows why. A restore tries it again, up to 3 times in a row. |
| =archived= | The work is done. No command starts it again.                                     |

An exit of Emacs marks its running instances =closed=, with =closed_by= set to =emacs-exit=. After a crash this cannot happen, so they stay =open=. An end of Emacs by a signal also runs the exit, so a restore takes both: the =open= instances of an Emacs that crashed, and the instances that the last Emacs closed at its exit.

*** Commands

| Command                                   | Description                                                      |
|-------------------------------------------+------------------------------------------------------------------|
| =M-x claude-code-ide-restore-sessions=      | Start again every instance that ran when the last Emacs ended (=C-u=: choose which) |
| =M-x claude-code-ide-reopen-session=        | Choose an instance that is not running and start it again        |
| =M-x claude-code-ide-archive-session=       | Mark an instance =archived=                                      |
| =M-x claude-code-ide-forget-session=        | Remove an instance from the registry (the transcript stays)      |
| =M-x claude-code-ide-list-session-registry= | List the registry: state, buffer, directory, last activity, title |

In the list, =RET= switches to a running instance or reopens a stopped one, =a= archives, =d= removes, and =R= restores.

*** Restore after a crash

1. Start Emacs. The mode reports how many instances can be restored.
2. Run =M-x claude-code-ide-restore-sessions=. The instances start one after the other, half a second apart; one that fails, or a =C-g=, does not stop the others, and the last start reports the result.
3. Each instance starts in its directory with =claude --resume <id>=, its instance name, its flags, the model of its last answer, and its title (=--name=, from =/rename=), so that other sessions find it by name.
4. Each instance gets =claude-code-ide-restore-note= as its first message. The default note says that the session was resumed after a crash, that its background tasks and unread messages from other sessions are gone, and that it must re-read its last state and re-arm its watches. Set the variable to =nil= to send no message.

The registry does not restore an instance that runs in this Emacs, that belongs to another live Emacs or to another host, or whose session id a running CLI process already has.

*** The state file

The state file holds only what Emacs knows. The conversation, its title and its model stay in the CLI transcript, =~/.claude/projects/<project>/<session-id>.jsonl=, and the registry reads them from there when it needs them.

#+begin_src json
{
  "version": 4,
  "sessions": [
    {
      "instance_id": "5afe576e-88a4-4ecf-b317-1cd4b509ca6d",
      "provider": "claude",
      "native_id": "5afe576e-88a4-4ecf-b317-1cd4b509ca6d",
      "generation": 1,
      "role": null,
      "transcript_path": "/home/me/.claude/projects/-home-me-src-app/5afe576e-88a4-4ecf-b317-1cd4b509ca6d.jsonl",
      "project_dir": "/home/me/src/app/",
      "buffer_name": "*claude-code[app:refactor]*",
      "instance_name": "refactor",
      "model": "opus",
      "extra_flags": "--permission-mode plan",
      "permission_mode": "plan",
      "state": "open",
      "started_at": "2026-11-03T09:12:44Z",
      "last_seen_at": "2026-11-03T09:12:44Z",
      "closed_at": null,
      "closed_by": null,
      "emacs_pid": 41022,
      "host": "laptop",
      "worktree": "/home/me/src/app/",
      "pid": 41388,
      "process_start_time": 1794201164.0,
      "emacs_start_time": 1794190002.0,
      "failure": null,
      "failure_count": 0,
      "failed_at": null,
      "native_id_generation": null,
      "chain": null,
      "handover": null
    }
  ]
}
#+end_src

- The state file is now =~/.emacs-claude-code-ide-state-v4.json= (=-v4= before the extension of =claude-code-ide-state-file=), with version 4. While it does not exist, the version 3 file (=-v3=), else the version 2 file (=-v2=), else the version 1 file, is read and migrated one time. Emacs never writes or moves the version 1, 2 or 3 file, so an older version of the package keeps working with its own file. docs/session-schema.md describes all versions.
- =chain= and =handover= (new in version 4) hold the handover chain of the instance and the last handover with it as its source; see [[*Handover][Handover]].
- =pid= and =process_start_time= identify the process of the last launch; a restore never starts an instance whose process still runs. =failure= and =failure_count= say why the last restore failed and how many restores failed in a row.
- =instance_id= is the instance ID, which never changes.
- =native_id= is the current CLI session id. Emacs starts a new conversation with =--session-id <new UUID>=. A SessionStart hook, passed with =--settings=, reports a new id after =/clear=, =/resume=, or a start with =-c= or =-r=. The reports go to a directory next to the state file (=claude-code-ide-session-registry-report-directory=).
- =provider=, =generation= and =role= say which CLI runs the instance, how often it was launched, and its optional role.
- If =claude-code-ide-cli-extra-flags= has its own =--settings=, the registry does not add its hook, because a second =--settings= replaces the first. Then a new id after =/clear= or =/resume= is not recorded.
- =model= and =extra_flags= come from =claude-code-ide-cli-extra-flags= at start. Session flags (=-c=, =-r=, =--resume=, =--session-id=, =--fork-session=) are not stored.
- =closed_by= is =exited= (the CLI ended), =killed= (Emacs ended a running CLI) or =emacs-exit=.

Every change goes through one queue. The queue writes under a lock directory (=<state-file>.lock=), writes a temporary file and renames it over the state file, and keeps the previous version as =<state-file>.bak=. If the state file cannot be read, the registry uses the =.bak= file, shows a warning, and on the next write copies the unreadable file aside (=.corrupt-<time>=) before it renames the new file over it.

** Session Status

The status buffer, =*Coding Agents Sessions*=, shows what each running instance does, grouped by project (the directory that the agent works in). The projects and instances that need you come first. Keep it open to see at a glance which sessions are blocked, and press =RET= to go to one; on a project line, =RET= goes to the first instance of that project.

#+begin_src elisp
(claude-code-ide-session-status-mode 1)   ; also turns on the session registry
#+end_src

The mode keeps the buffer up to date, but it does not show it. =M-x claude-code-ide-show-session-status= shows it as a normal buffer, in the selected window (=claude-code-ide-session-status-display-action= changes that, for example to a side window). Turn the mode off to kill the buffer.

Codex instances are in the same buffer. Each line shows the provider, the model (=unknown= when not known), and the common state with its reason (a =?= marks a guess).

- A Codex start asks you to trust its status hooks when they are not trusted yet (see Codex). =M-x claude-code-ide-codex-trust-hooks= is the manual way, for example after a no: it shows the hooks and, after a confirmation, trusts them in =~/.codex/config.toml=. An instance that started without hooks gets status after its restart.
- =claude-code-ide-codex-events-trust-timeout= (default 5) is the number of seconds that a start from a command waits for the hook trust check.
- =claude-code-ide-session-status-hook-time-limit= (default 10) is the number of seconds that a status hook waits for its lock under a heavy load. After that, it drops its event, writes a line to =hook-errors.log= in the events folder, and exits, so that it never holds up the CLI for longer. The status buffer then says how many events were dropped; RET on that line shows the log.
  - Claude Code and Codex give each hook this limit plus 5 seconds, so a hook gives up before the CLI stops it.
  - A new value changes the Codex hook definitions: the next Codex start from a command asks you once to trust the hooks again.
  - The value is written into the hook scripts of the report directory, which all Emacs processes with the same state file share; the last start sets it for all of them.
- =claude-code-ide-session-status-snapshot= (default =t=) writes =<report directory>/status/<emacs pid>.json= for coordinators; see [[file:docs/status-schema.md][docs/status-schema.md]].

Each state says who waits for whom. They are listed in the order of the buffer: what needs you first.

| State            | Meaning                                                                                       |
|------------------+-----------------------------------------------------------------------------------------------|
| =NEEDS ANSWER=   | A permission dialog, a question menu, a plan approval or an MCP input form is open. The agent is blocked until you answer |
| =ASKS YOU=       | The turn ended with a reply that asks you something (by default, a line that ends with "?"). The agent waits for your answer, also while its tasks run |
| =FAILED=         | The turn ended with an API error                                                              |
| =NO SIGNAL=      | The instance sent nothing since it started, for example at the dialog that asks whether to trust the folder |
| =TASKS QUIET=    | The turn ended and the background subagents show no activity for a long time. Look at it: one may hang |
| =WAITS FOR YOU=  | The turn ended. The agent waits for your next message. Background shells (tests, watchers, servers) may still run; the detail names them |
| =WAITS ON TASKS= | The turn ended, but its subagents still run. The agent continues by itself when they finish |
| =STARTING=       | The instance has started and has not reported yet                                             |
| =WORKING=        | The agent works                                                                               |
| =UNTRACKED=      | The instance started without status hooks, and Emacs knows no CLI process of it                |

The =For= column shows how long the instance has been in its state. =Detail= shows the command or question that waits for you, the first line of the last reply, or the running tasks (for example "2 agents, 1 shell: Run the tests").

| Command                                | Description                                              |
|----------------------------------------+----------------------------------------------------------|
| =M-x claude-code-ide-show-session-status=  | Show the status buffer                                   |
| =M-x claude-code-ide-visit-waiting-session= | Go to the first session in the list that needs you        |

In the buffer, =RET= goes to the session on the line, and =w= goes to the first session that needs you, in the order of the table; the longest wait first within each state. While the mode is on, the mode line shows =Claude[N need you]= when instances are in one of the first four states.

*** How it works

The registry passes Claude Code hooks to each instance it starts. Each hook runs a small shell script that writes the hook input to a file, numbered per instance, in a directory next to the state file. Emacs reads the files in order, deletes them, and updates the status. The script prints nothing and always exits with 0, so it never changes what Claude does. Each hook has a timeout of =claude-code-ide-session-status-hook-time-limit= plus 5 seconds (15 s at the default).

- After you approve a command, the status stays =NEEDS ANSWER= until the command ends, because no hook fires on the approval.
- Claude Code starts subagents in the background, so the main turn often ends while they work. The list of running tasks comes with the end of each turn, and the subagents report their own steps. Subagents are quiet after =claude-code-ide-session-status-agent-quiet-time= seconds (600) without activity, or after =claude-code-ide-session-status-task-quiet-time= seconds (900) while one runs a long command.
- A background shell does not keep the agent from you: the agent often starts tests, a watcher or a server in the background and then asks you something. Claude Code itself reports that it waits for your input while shells run, but not while subagents run.
- =claude-code-ide-session-status-ask-regexps= sets which lines of a reply ask you something. For example, add ="\\`Next for Raymond:"= when your sessions end their replies with such a line.
- An interrupt (=Esc=) fires no hook. When a working instance sends no event for =claude-code-ide-session-status-quiet-time= seconds, Emacs checks two things. If the new part of the transcript has an interrupt marker (an interrupt during a tool), the state becomes =WAITS FOR YOU= with "Interrupted". If the terminal no longer shows Claude's spinner line (for example "✢ Misting… (3s)"), the state becomes =WAITS FOR YOU= with "Interrupted?". If a later version of Claude Code changes the spinner, this check shows a working instance as =WAITS FOR YOU=; it never shows a waiting instance as working. When the spinner shows again, or the agent uses a tool, the state is =WORKING= again.
- A turn that a queued prompt, a message from another session or a task notification starts fires no prompt hook. Its first tool use, or its record in the transcript, shows the instance as =WORKING=.
- A denial with =Esc= fires no hook either. The instance stays =NEEDS ANSWER= until Claude reports, 60 seconds later, that it waits for your input.
- Set =claude-code-ide-session-status-tracking= to =nil= to start instances without status hooks.

Once enabled, Claude can use these tools to navigate your codebase. For example:
- "Find the definition of function foo"
- "Show me all places where this variable is used"
- "What type of AST node is under the cursor?"
- "Analyze the parse tree of this entire file"
- "List all functions and variables in this file"
- "How many files are in this project?"

*** Routing, secrets and scopes

- Each instance gets a secret at each launch. =claude-code-ide-mcp-server-secret-placement= (default =header=) says where the generated config puts it: in the =X-Emacs-MCP-Instance-Secret= header, or in the URL path.
- Claude Code gets its MCP config in a file (=--mcp-config FILE=), not on its command line, so =ps= does not show the secret or other header values. The file has mode 0600, in a private 0700 folder (=claude-code-ide-mcp-config-directory=, default =claude-code-ide-<uid>= in the temporary folder). If that folder belongs to another user or cannot be used, Emacs makes a new private folder with =make-temp-file= instead. Emacs deletes the file when the instance ends, when its start fails, and when Emacs quits. The first write in an Emacs also deletes the files of Emacs processes that no longer run.
- The debug log never shows the secret, the coordinator credential, or another header value.
- Tools with =:scope coordinator= run only for requests with the coordinator credential, from =claude-code-ide-mcp-server-coordinator-credential-file= (default: =coordinator-credential= in the report directory, mode 0600). =M-x claude-code-ide-mcp-server-rotate-coordinator-credential= replaces it.
- The tool =get_capabilities= lists the operations of the calling instance.
- =claude-code-ide-mcp-server-extra-headers= adds headers (for example a global token) to the generated MCP config. A value can be a function that returns it.
- The server refuses requests with an =Origin= header, requests that are not =application/json=, and requests without a known session.
- See [[file:docs/api-mcp.md][docs/api-mcp.md]].

** Control for Coordinators

- The control operations list, inspect, launch, resume, prompt, and stop an instance by its instance ID. Each is an Elisp function (=claude-code-ide-control-...=) and an MCP coordinator tool. See [[file:docs/api-control.md][docs/api-control.md]].
- A prompt goes through the instance's inbox in =<report directory>/inbox/=. It is sent only when the instance is idle, and it counts as delivered when the CLI reports the same prompt.
- Options: =claude-code-ide-control-inbox-directory=, =claude-code-ide-control-ack-timeout=, =claude-code-ide-control-retry-interval=, =claude-code-ide-control-enable-mcp-tools=, =claude-code-ide-control-done-days= (default 7).

** Handover

- =M-x claude-code-ide-handover= hands the work of an instance to a new conversation of the same or the other provider (Claude Code or Codex). The source stops; the target gets a short first prompt that points to the handover document in =.handover/= of the worktree, and writes a state summary there. The source never needs one more turn, so a handover works at a quota limit.
- In the status buffer, =H= offers a handover of the session on the line, or of the first session at a quota limit. Emacs never starts a handover by itself.
- Before the source stops, Emacs checks that the target CLI is found, that no other instance runs in the worktree, and, for a Codex target, that its status hooks are trusted (it asks you for the trust).
- Processes that still run in the worktree after the stop are shown with their process ID, command and folder: end them, wait, or cancel. While a handover runs, no other instance starts in its worktree.
- Each stage is saved in the session registry before it runs. After a crash, the handover continues when the registry mode starts (=claude-code-ide-handover-recover-at-start=, default t): before the stop it is cancelled, after it only the target is resumed or started again, never the source. =M-x claude-code-ide-handover-recover= runs the same recovery.
- After the commit, the queued prompts and review results of the source go to the target.
- =M-x claude-code-ide-handover-resolve= answers a handover that needs you, and =M-x claude-code-ide-handover-cancel= cancels one.
- Coordinators use the MCP tools =claude-code-ide-control-handover= and =claude-code-ide-control-handover-status=. Agents can ask with =request_handover=; Emacs then asks you after their turn.
- Options: =claude-code-ide-handover-quiesce-timeout=, =claude-code-ide-handover-delivery-timeout= (600 s for the target to get the document), =claude-code-ide-handover-watch-interval= (5 s), =claude-code-ide-handover-ack-wait= (10 s for the acknowledgement of a prompt that the source got), =claude-code-ide-handover-stray-wait=, =claude-code-ide-handover-directory=, =claude-code-ide-handover-session-server-detection=, =claude-code-ide-handover-budget=, =claude-code-ide-handover-recover-at-start=, =claude-code-ide-handover-enable-request-tool=.
- See [[file:docs/handover.md][docs/handover.md]].

** Reviews

- A review is an external process whose result belongs to one instance. =claude-code-ide-review-track= (and the coordinator tool =claude-code-ide-control-track-review=) records it.
- When the process ends, Emacs reads the result file and puts the result into the instance's inbox. The instance gets it one time, when it can take it. A missing or broken result file gives an explicit error result.
- After a handover, the result goes to the current instance of the chain. A review that ends while Emacs does not run is delivered at the next start.
- The output of a review command never goes into a prompt or a record.
- Options: =claude-code-ide-review-directory=, =claude-code-ide-review-check-interval=, =claude-code-ide-review-retry-seconds=, =claude-code-ide-review-max-result-chars=, =claude-code-ide-review-done-days=, =claude-code-ide-review-format-function=.
- See [[file:docs/review.md][docs/review.md]].

** Creating Custom MCP Tools

You can expose your own Emacs functions to Claude through the MCP tools system. This allows Claude to interact with specialized Emacs features, custom commands, or domain-specific functionality.

*** Tool Definition Format

Define tools using the =claude-code-ide-make-tool= function:

#+begin_src emacs-lisp
(claude-code-ide-make-tool
 :function #'function-name     ; The Emacs function to call
 :name "tool_name"             ; Name for Claude to use (snake_case recommended)
 :description "..."            ; Human-readable description
 :args '((:name "param1"       ; List of argument specifications
          :type string         ; Type: string, number, integer, boolean, etc.
          :description "..."   ; What this parameter does
          :optional t)))       ; Optional parameters marked with :optional t
#+end_src

Available argument types: =string=, =number=, =integer=, =boolean=, =array=, =object=, =null=

*** Context-Aware Tool Example

#+begin_src emacs-lisp
;; Define a context-aware function that operates in the session's project
(defun my-project-grep (pattern)
  "Search for PATTERN in the current session's project."
  (claude-code-ide-mcp-server-with-session-context nil
    ;; This executes with the session's project directory as default-directory
    (let* ((project-dir default-directory)
           (results (shell-command-to-string
                    (format "rg -n '%s' %s" pattern project-dir))))
      results)))

;; Define and register the tool (automatically added to claude-code-ide-mcp-server-tools)
(claude-code-ide-make-tool
 :function #'my-project-grep
 :name "my_project_grep"
 :description "Search for pattern in project files"
 :args '((:name "pattern"
          :type string
          :description "Pattern to search for")))

;; Enable Emacs tool MCP server
(claude-code-ide-emacs-tools-setup)
#+end_src

The =claude-code-ide-mcp-server-with-session-context= macro ensures your tool executes in the correct project context.
